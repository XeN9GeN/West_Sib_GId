# 1. Назначение документа

Данный документ определяет требования к переработке системы поиска, классификации, хранения и отображения объектов культурного наследия и туристической инфраструктуры в проекте West_Sib_GId.

Документ предназначен не для общего ознакомления с проектом, а для использования в качестве **строгой спецификации при разработке программного кода ИИ-агентом GitHub Copilot**.

Copilot должен руководствоваться описанными ниже правилами при:
- изменении существующих моделей данных;
- разработке системы классификации объектов;
- импорте и обогащении данных OpenStreetMap;
- использовании дополнительных источников информации;
- отборе объектов по пространственным критериям;
- формировании ответов API;
- реализации логики отображения объектов на интерактивной карте;
- написании миграций и тестов.

Главная цель — перейти от механического отображения всех найденных объектов OSM к **контролируемой системе отбора географически релевантных, культурно значимых и туристически интересных объектов**.

Система должна обеспечивать воспроизводимость классификации, сохранение исходных данных, возможность ручной корректировки и предсказуемое поведение при повторном импорте.

# 2. Общая концепция системы

## 2.1. Основной принцип

Не каждый объект, найденный в OpenStreetMap или сторонних источниках, должен становиться объектом пользовательской карты.

Наличие объекта в OSM, наличие тега `historic=*`, `tourism=*` или попадание в категорию `monument` само по себе не является достаточным основанием для отображения.

Каждый объект должен пройти последовательность проверок:

1. Географическая релевантность относительно железнодорожной инфраструктуры.
2. Соответствие разрешённым типам объектов.
3. Проверка культурной или туристической значимости.
4. Классификация по единой таксономии.
5. Проверка качества доступной информации.
6. Определение статуса отображения.
7. Применение правил отображения в зависимости от масштаба карты.

Упрощённая схема:

`Источники → Пространственный отбор → Белый список → Классификация → Проверка значимости → БД → API → Фильтрация по zoom → Карта`

## 2.2. Разделение ответственности

Система должна различать четыре независимых аспекта объекта:

| Аспект | Назначение | Пример |
|---|---|---|
| Категория | Общий тип объекта | Историческое наследие |
| Подкатегория | Конкретный тип | Железнодорожная техника |
| Класс объекта | Его назначение и характер | Культурное наследие / туризм |
| Статус отображения | Допущен ли объект на карту | `visible` / `excluded_from_map` |

Дополнительно объект может иметь приоритет отображения и оценку качества описания.

**Запрещается смешивать эти аспекты в одном поле.**

Например, `monument`, `tourism` и `heritage` не должны использоваться как взаимозаменяемые значения одного классификационного признака.

## 2.3. Принцип сохранения данных

Исключение объекта из пользовательской карты не должно означать его физическое удаление из базы данных.

Объект может быть:
- сохранён в БД;
- исключён из пользовательской карты;
- доступен для последующей переклассификации;
- повторно допущен на карту после появления дополнительных сведений.

Основной механизм исключения — `excluded_from_map` с обязательной причиной исключения.

# 3. Пространственные требования

## 3.1. Максимальный радиус от железной дороги

**Требование R-001: объект допускается к пользовательской карте только при наличии пространственной связи с железнодорожной инфраструктурой в радиусе не более 2500 метров.**

Радиус рассчитывается относительно координат железнодорожной линии, представленных в системе данных проекта.

Условия:
- расстояние — не более 2500 метров;
- учитываются все релевантные координаты железнодорожной линии;
- расстояние должно рассчитываться географически корректно;
- нельзя заменять проверку расстояния простым сравнением широты и долготы;
- должны учитываться все необходимые участки железнодорожной сети, уже используемые проектом.

Если объект находится дальше 2500 метров, он не должен попадать в пользовательский набор объектов.

## 3.2. Единый источник пространственного ограничения

Проверка радиуса должна быть согласована между всеми этапами обработки данных.

Необходимо проверить:
- `scripts/import_osm.py`;
- `select_osm_pois_near_railway`;
- `promote_selected_pois` в `enrich_osm.py`;
- параметр `-RadiusMeters` в `start_project.ps1`;
- API, если оно допускает получение объектов вне предварительно отфильтрованного набора.

Если пространственный фильтр применяется на этапе импорта, последующие этапы не должны случайно обходить его.

Рекомендуемое значение по умолчанию — `2500`.

Если радиус настраивается параметром запуска, значение по умолчанию должно оставаться равным 2500 метрам. Возможность изменить его не должна приводить к тому, что пользовательская карта по умолчанию показывает объекты за пределами установленного радиуса.

## 3.3. Повторная проверка

При продвижении объекта из промежуточного набора в основную таблицу необходимо повторно проверять пространственное условие.

Это защищает систему от:
- объектов, добавленных вручную;
- старых записей, созданных при предыдущем радиусе 5000 метров;
- ошибок промежуточной обработки;
- некорректного повторного импорта.

## 3.4. Критерии приёмки

- В пользовательской таблице нет объектов, расстояние до ближайшей релевантной железнодорожной координаты которых превышает 2500 метров.
- Объект на расстоянии ровно 2500 метров не исключается из-за строгого сравнения `>` вместо `>=`.
- Повторный импорт не добавляет объекты за пределами установленного радиуса.
- Параметр запуска проекта использует 2500 метров по умолчанию.
- Проверка расстояния использует географические вычисления PostGIS, а не приблизительную арифметику координат.

# 4. Таксономия объектов

## 4.1. Общие требования

Необходимо разработать единую таксономию объектов, которая будет использоваться при:
- извлечении объектов из OSM;
- обогащении информации;
- сохранении в БД;
- работе API;
- отображении фильтров и маркеров на фронтенде.

Таксономия должна быть централизованной.

**Запрещается поддерживать независимые списки категорий в нескольких частях проекта без единого источника истины.**

В качестве предпочтительного решения рассматривается машиночитаемый конфигурационный файл:

`config/taxonomy.yaml`

Формат и расположение должны быть окончательно согласованы Claude с текущей архитектурой.

Конфигурация должна содержать:
- идентификаторы категорий;
- названия категорий;
- подкатегории;
- синонимы;
- соответствующие OSM-теги;
- признаки культурной и туристической принадлежности;
- правила включения;
- правила исключения;
- приоритеты отображения;
- правила классификации;
- при необходимости — ограничения по zoom.

## 4.2. Предлагаемая иерархия

Предлагается использовать следующие основные группы.

### A. Историческое и культурное наследие

Объекты, имеющие историческую, мемориальную, архитектурную, культурную или иную общественную ценность.

Подкатегории:

| Подкатегория | Состав |
|---|---|
| `monuments_memorials` | Памятники, мемориалы, обелиски, стелы, памятные знаки |
| `railway_heritage` | Исторические вокзалы, паровозы, локомотивы, железнодорожные музеи, исторические станции |
| `historical_architecture` | Исторические здания, усадьбы, архитектурные ансамбли |
| `industrial_heritage` | Исторические заводы, фабрики, промышленные сооружения |
| `archaeological_sites` | Городища, археологические памятники, древние поселения |
| `military_heritage` | Мемориалы, историческая военная техника, памятные комплексы |

### B. Культурные учреждения

Действующие или исторически значимые учреждения, связанные с культурой и сохранением знаний.

| Подкатегория | Состав |
|---|---|
| `historical_museums` | Исторические, краеведческие музеи |
| `art_museums` | Художественные музеи, галереи |
| `specialized_museums` | Технические, железнодорожные, отраслевые музеи |
| `theatres` | Драматические театры |
| `children_theatres` | Детские театры, театры кукол |
| `concert_venues` | Филармонии, концертные и органные залы |
| `cultural_centres` | Значимые культурные центры, дома культуры |

### C. Религиозное наследие

| Подкатегория | Состав |
|---|---|
| `orthodox_churches` | Православные церкви, соборы, монастыри |
| `other_christian_sites` | Католические, протестантские и другие христианские объекты |
| `mosques` | Мечети |
| `synagogues` | Синагоги |
| `buddhist_sites` | Буддийские храмы, монастыри и центры |
| `other_religious_sites` | Другие религиозные объекты, обладающие значимостью |

Конфессиональная принадлежность должна сохраняться в данных, даже если фронтенд объединяет все объекты в одну группу «Религиозные объекты».

### D. Природное наследие

| Подкатегория | Состав |
|---|---|
| `natural_monuments` | Уникальные природные объекты |
| `protected_areas` | Заповедники, природные парки и охраняемые территории |
| `lakes` | Озёра и значимые водоёмы |
| `rivers` | Значимые реки и природные участки |
| `forests` | Природные лесные территории, имеющие самостоятельную ценность |

Обычный водоём, лесной участок или река не должны автоматически считаться туристически значимыми объектами.

### E. Туристические и рекреационные объекты

| Подкатегория | Состав |
|---|---|
| `zoos` | Зоопарки как целостные объекты |
| `planetariums` | Планетарии |
| `circuses` | Цирки |
| `parks` | Значимые парки и рекреационные территории |
| `art_objects` | Общественно значимые арт-объекты |

Наличие туристического назначения не означает автоматически наличие статуса культурного наследия.

## 4.3. Синонимичная группировка

Разные исходные типы должны объединяться в единую пользовательскую категорию, если они обозначают близкие по смыслу объекты.

Примеры:

| Исходные обозначения | Единая категория |
|---|---|
| Памятник, мемориал, памятный знак, обелиск, стела | Памятники и мемориалы |
| Собор, церковь, храм, часовня | Религиозные объекты |
| Мечеть, синагога, костёл, буддийский храм | Религиозные объекты с сохранением подтипа |
| Краеведческий музей, исторический музей | Исторические музеи |
| Художественный музей, картинная галерея | Художественные музеи и галереи |
| Драматический театр | Театры |
| Театр кукол, детский театр | Детские театры |
| Филармония, концертный зал, органный зал | Концертные площадки |
| Вечный огонь, братская могила, мемориал Славы | Мемориальные объекты |

Синонимичная группировка не должна приводить к потере исходной информации.

В БД необходимо сохранять исходные OSM-теги и, по возможности, исходный тип объекта.

## 4.4. Правило самостоятельной категории железнодорожного наследия

**Требование R-004: железнодорожное наследие должно быть выделено в самостоятельную категорию или подкатегорию, а не растворяться в `monument`, `architecture` или `museum`.**

К потенциальным объектам железнодорожного наследия относятся:

- исторические железнодорожные вокзалы;
- исторические здания станций;
- паровозы и локомотивы;
- памятники железнодорожной технике;
- исторические вагоны;
- железнодорожные музеи;
- музейные экспозиции железнодорожной тематики;
- исторические железнодорожные сооружения;
- другие объекты, непосредственно связанные с историей железнодорожного транспорта.

Возможные OSM-признаки для поиска:

- `historic=locomotive`;
- `historic=railway_station`;
- `railway=museum`;
- `railway=station` совместно с признаками исторической значимости;
- `building=train_station`;
- `tourism=museum` совместно с `museum=railway`;
- другие релевантные сочетания тегов.

Это предварительный список, а не исчерпывающая спецификация OSM.

Claude должен проверить применимость тегов, их значения и совместимость с текущим импортом.

**Важно:** не всякая железнодорожная станция является объектом наследия. Обычная действующая станция не должна автоматически получать статус `railway_heritage`.

Для включения должны присутствовать признаки исторической, музейной, архитектурной или мемориальной значимости.

# 5. Разделение культурного наследия и туризма

## 5.1. Основной принцип

Культурное наследие и туристические объекты — не одно и то же.

Культурное наследие определяется исторической, архитектурной, мемориальной, археологической, религиозной или иной культурной ценностью.

Туристический объект определяется самостоятельной привлекательностью для посещения, отдыха, знакомства с местностью или получения впечатлений.

Примеры:

| Объект | Культурное наследие | Туризм |
|---|---|---|
| Исторический вокзал | Да | Возможно |
| Паровоз-памятник | Да | Да |
| Исторический музей | Да | Да |
| Современный планетарий | Нет или не подтверждено | Да |
| Зоопарк | Не автоматически | Да |
| Обычный парк аттракционов | Нет | Да |
| Мемориал | Да | Возможно |
| Историческая усадьба | Да | Да |
| Обычный торговый объект | Нет | Не включать |

## 5.2. Модель классификации

Рекомендуется использовать независимый признак, например:

`object_class`

Допустимые значения:
- `heritage`;
- `tourism`;
- `both`;
- `unclassified`.

Если архитектура БД поддерживает массивы или связанные справочники, допускается иная реализация, сохраняющая ту же семантику.

**Не рекомендуется создавать отдельные дублирующие записи для одного объекта только потому, что он одновременно относится к наследию и туризму.**

Один объект может иметь несколько признаков принадлежности.

## 5.3. Признаки культурного наследия

При определении статуса наследия учитывать:

1. Официальный статус охраны объекта.
2. Наличие записи в государственных реестрах объектов культурного наследия.
3. Наличие признаков охраны в Wikidata.
4. Теги OSM, связанные с историческим и культурным наследием.
5. Историческую значимость, подтверждённую авторитетными источниками.
6. Наличие достоверной информации об историческом назначении объекта.

Возможные источники и признаки:
- `heritage=*`;
- `ref:mkrf_*` и другие релевантные идентификаторы реестров;
- Wikidata `P1435` (heritage designation);
- официальные государственные реестры;
- материалы региональных органов охраны культурного наследия.

Само отсутствие официального статуса охраны не означает, что объект не имеет культурной ценности. Однако в таком случае основание для классификации должно быть подтверждено другими источниками.

## 5.4. Признаки туристического объекта

При определении туристической принадлежности учитывать:
- самостоятельную привлекательность объекта;
- возможность посещения;
- известность или региональную значимость;
- наличие подтверждённого туристического назначения;
- наличие описания, информации о посещении или туристического статуса в авторитетных источниках.

Тег `tourism=attraction` может быть основанием для рассмотрения объекта, но не гарантирует его включение.

# 6. Белый список объектов и исключения

## 6.1. Двухэтапная фильтрация

Необходимо реализовать два независимых механизма:

**Этап 1. Белый список кандидатов.**

На этом этапе определяются типы OSM-объектов, которые потенциально могут представлять культурный или туристический интерес.

**Этап 2. Классификатор и проверка значимости.**

На этом этапе объект получает категорию, подкатегорию, класс и решение о возможности отображения.

Наличие тега из белого списка не означает автоматическое включение на карту.

## 6.2. Белый список

Белый список должен строиться на основании официальной схемы тегов OSM и проверенных практических примеров.

Рекомендуемые группы:

| Группа | Потенциальные признаки |
|---|---|
| Исторические объекты | `historic=*` |
| Памятники | `historic=monument`, `historic=memorial`, `historic=wayside_shrine` |
| Архитектурное наследие | `building=*` совместно с признаками исторической ценности |
| Музеи | `tourism=museum` |
| Галереи | `tourism=gallery` |
| Театры | `amenity=theatre` |
| Религиозные объекты | `amenity=place_of_worship` |
| Железнодорожное наследие | Релевантные сочетания `railway=*`, `historic=*`, `tourism=*`, `building=*` |
| Природные объекты | Релевантные значения `natural=*`, `leisure=*`, `boundary=protected_area` |
| Туристические объекты | Релевантные значения `tourism=*` |

Это список кандидатов, а не безусловное разрешение на отображение всех объектов с указанными тегами.

## 6.3. Исключаемые объекты

Объекты следующих типов должны исключаться из пользовательской карты, если отсутствуют дополнительные подтверждения их значимости:

- обычные технические сооружения;
- административные здания без самостоятельной культурной ценности;
- обычные школы и учебные учреждения;
- отдельные вольеры и животные зоопарков;
- отдельные аттракционы внутри развлекательных комплексов;
- случайные арт-объекты без подтверждённой общественной или культурной ценности;
- обычные объекты инфраструктуры;
- незначимые заброшенные здания;
- технические объекты, не представляющие интереса для посетителя;
- объекты с ошибочными или неполными тегами, не позволяющими установить их назначение.

Отдельно необходимо проверять:
- памятные доски;
- локальные памятники;
- скульптуры;
- стелы;
- аллеи;
- мемориальные комплексы;
- исторические промышленные сооружения;
- старые вокзалы;
- водонапорные башни;
- исторические мосты.

Их нельзя автоматически исключать только по названию или типу.

## 6.4. Правило исключения

Для исключения объекта использовать:

`excluded_from_map = true`

Дополнительно сохранять причину:

`exclusion_reason`

Рекомендуемые причины:
- `outside_railway_radius`;
- `unsupported_object_type`;
- `insufficient_cultural_significance`;
- `insufficient_tourism_value`;
- `duplicate_or_component`;
- `technical_infrastructure`;
- `individual_zoo_animal_or_enclosure`;
- `invalid_or_incomplete_data`;
- `manual_exclusion`;
- `pending_review`.

Финальный набор причин может быть расширен при проектировании модели.

Если объект ещё не классифицирован, не следует автоматически считать его культурно значимым.

Для неоднозначных случаев предпочтительно использовать статус ручной проверки, а не безусловное включение.

## 6.5. Сохранение исходной информации

При исключении:
- не удалять запись физически;
- не удалять исходные OSM-теги;
- не терять координаты;
- не удалять внешние идентификаторы;
- сохранять причину исключения;
- сохранять возможность пересмотра классификации.

# 7. Особые требования к категории `monument`

## 7.1. Запрет на автоматическое отображение

**Требование R-005: категория `monument` не должна автоматически означать, что объект допускается к отображению на карте.**

Существующая категория слишком широкая и может объединять принципиально разные объекты.

В частности, внутри неё могут находиться:
- памятники историческим личностям;
- военные мемориалы;
- памятные доски;
- памятные знаки;
- локальные скульптуры;
- паровозы и другая железнодорожная техника;
- военная техника;
- арт-объекты;
- случайные туристические аттракционы;
- другие объекты, не имеющие самостоятельной культурной ценности.

## 7.2. Требуемая декомпозиция

Исходный `monument` должен быть разделён на более точные подкатегории.

| Новая подкатегория | Примеры |
|---|---|
| `monuments_memorials` | Памятники, мемориальные комплексы |
| `memorial_plaques` | Памятные доски, мемориальные таблички |
| `military_memorials` | Мемориалы военной истории |
| `railway_heritage` | Памятники-паровозы, исторические локомотивы |
| `military_heritage` | Историческая военная техника |
| `art_objects` | Самостоятельные общественно значимые арт-объекты |

Подкатегория не определяет автоматически значимость.

Например, наличие скульптуры не является достаточным условием для её включения.

## 7.3. Проверка каждого типа

Классификатор должен учитывать:
- OSM-теги;
- название;
- описание;
- Wikidata;
- Wikipedia;
- официальные источники;
- дополнительные признаки, подтверждающие историческое или культурное назначение.

Если данных недостаточно, объект получает статус `pending_review` либо исключается из пользовательского слоя до подтверждения.

# 8. Требования к поиску информации в WWW

## 8.1. Основной принцип

Поиск информации должен быть направленным.

Нельзя искать объекты без ограничений, а затем автоматически добавлять всё найденное в БД.

Каждый поиск должен опираться на заранее определённую таксономию, белый список тегов и критерии значимости.

## 8.2. Источники информации

Приоритет источников:

**Уровень 1 — первичные и официальные источники**
- OpenStreetMap;
- официальные государственные реестры;
- региональные органы охраны культурного наследия;
- официальные сайты музеев и учреждений;
- сайты муниципальных и региональных администраций;
- официальные сайты объектов.

**Уровень 2 — авторитетные справочные источники**
- Wikidata;
- Wikipedia;
- Wikivoyage;
- региональные туристические порталы;
- научные и исторические публикации.

**Уровень 3 — дополнительные источники**
- локальные туристические сайты;
- краеведческие ресурсы;
- информационные порталы;
- другие проверяемые публикации.

Информация из источников третьего уровня не должна автоматически перевешивать официальные сведения.

## 8.3. Что искать

Для каждого объекта желательно получить:
- официальное или общепринятое название;
- тип объекта;
- историческое назначение;
- краткое описание;
- местоположение;
- историческую или культурную значимость;
- туристическую привлекательность;
- статус охраны;
- дату основания или создания, если известна;
- ссылку на источник;
- идентификаторы Wikidata/Wikipedia, если имеются.

Необязательно, чтобы все поля были заполнены.

Отсутствие дополнительных сведений не должно приводить к выдумыванию информации.

## 8.4. Правило подтверждения

ИИ-классификатор не должен считать собственную догадку подтверждённым фактом.

Для каждого решения о включении или присвоении статуса наследия желательно сохранять:
- источник;
- ссылку;
- тип подтверждаемого факта;
- результат проверки;
- дату получения информации.

Если источник не подтверждает культурную значимость, нельзя приписывать её объекту только на основании названия.

## 8.5. Обработка противоречий

Если источники противоречат друг другу:
1. Сначала проверить официальный источник.
2. Затем проверить независимые авторитетные источники.
3. Не заменять достоверные исходные данные предположениями.
4. Зафиксировать неопределённость.
5. При невозможности разрешить противоречие направить объект на ручную проверку.

# 9. Требования к `short_description`

## 9.1. Основное правило

**Требование R-002: на крупных масштабах карты отображаются только объекты с содержательным `short_description`.**

Наличие поля в БД само по себе недостаточно.

Описание должно:
- быть непустым;
- содержать полезную информацию об объекте;
- не быть технической заглушкой;
- не состоять только из названия и типа объекта;
- не содержать автоматически сформированную бессодержательную фразу;
- соответствовать конкретному объекту.

Примеры недостаточных описаний:
- «Музей в Омске».
- «Памятник в Новосибирске».
- «Церковь».
- Повторение названия объекта без дополнительной информации.

Примеры содержательных описаний:
- описание исторического назначения;
- краткая информация о событии или личности, с которыми связан памятник;
- сведения об архитектурной особенности здания;
- история железнодорожного сооружения;
- информация о музейной экспозиции.

## 9.2. Источники описания

Текущая логика получения `short_description` должна быть проверена.

По предварительному описанию Claude, сейчас могут использоваться:
- `description:ru`;
- Wikipedia;
- Wikidata;
- `description`;
- Wikivoyage.

Необходимо сохранять информацию о происхождении описания.

Рекомендуемые дополнительные поля:
- `description_source`;
- `description_quality`;
- `description_checked_at`.

## 9.3. Минимальные критерии качества

Рекомендуется реализовать отдельную проверку качества описания.

Она должна учитывать:
1. Непустое содержимое после `trim`.
2. Достаточную информативность.
3. Отсутствие шаблонных заглушек.
4. Отсутствие простого повторения названия.
5. Связь текста с конкретным объектом.

Минимальная длина должна быть настраиваемой в конфигурации.

В качестве начального ориентира можно протестировать порог 40–60 символов, но окончательное значение должно быть выбрано после проверки реальных описаний проекта.

Нельзя считать длину единственным критерием качества.

## 9.4. `ai_summary`

Необходимо отдельно определить роль `ai_summary`.

Предварительное правило:

- `ai_summary` не заменяет автоматически `short_description`;
- AI-сгенерированный текст не считается подтверждённым описанием только потому, что он существует;
- он может использоваться для отображения, если прошёл проверку качества и соответствует требованиям к достоверности;
- происхождение текста должно сохраняться;
- нельзя перезаписывать подтверждённое описание неподтверждённым AI-текстом.

Claude должен проверить существующий контракт `ai_summary` и предложить совместимый вариант реализации.

## 9.5. Критерии приёмки

На крупных масштабах:
- объект без содержательного описания не отображается;
- объект с `NULL`, пустой строкой или строкой из пробелов не отображается;
- объект с бессодержательной заглушкой не отображается;
- объект с подтверждённым качественным описанием может отображаться при выполнении остальных условий.

# 10. Правила отображения по масштабу карты

## 10.1. Общая концепция

Отображение должно зависеть от zoom.

Чем дальше масштаб карты, тем более значимые и информативные объекты должны оставаться видимыми.

При приближении пользователь получает доступ к более подробным объектам.

При этом необходимо учитывать, что наличие объекта в API и его фактическое отображение на карте — разные вещи.

## 10.2. Основное правило

На крупных масштабах карты отображаются только объекты, имеющие содержательный `short_description`.

Под крупным масштабом здесь понимается приближённое отображение карты, при котором пользователь рассматривает отдельные объекты и их окрестности.

## 10.3. Предлагаемые уровни

| Уровень | Zoom (предварительно) | Условия |
|---|---|---|
| Обзорный | 5–8 | Только наиболее значимые объекты, если они удовлетворяют правилам качества и плотности |
| Региональный | 9–12 | Основные культурные и туристические объекты |
| Городской | 13–15 | Дополнительные локальные объекты |
| Детальный | 16–17+ | Более полный набор допущенных объектов, но только в пределах остальных фильтров |

Значения являются стартовыми гипотезами.

Claude должен проверить используемую картографическую библиотеку и существующую систему масштабирования.

Окончательные пороги должны быть настраиваемыми, а не разбросанными по коду.

## 10.4. Фильтрация на сервере

Рекомендуется реализовать фильтрацию по zoom на уровне API.

API должно:
- принимать текущий zoom;
- учитывать географический bbox;
- учитывать статус исключения;
- учитывать радиус от железной дороги;
- учитывать критерии качества описания;
- применять правила видимости;
- возвращать только объекты, подходящие для текущего масштаба.

Нельзя полагаться исключительно на фильтрацию JavaScript на клиенте, если сервер может отдавать заведомо ненужные объекты.

## 10.5. Фронтенд

Необходимо проверить:
- обновление данных при изменении bbox;
- обновление данных при изменении zoom;
- обработку события `zoomend`;
- совместимость с существующим `moveend`;
- повторную загрузку данных при изменении масштаба;
- отсутствие лишних запросов при незначительных изменениях карты.

Если API начинает учитывать zoom, фронтенд должен передавать актуальное значение масштаба.

# 11. Архитектура централизованной таксономии

## 11.1. Единый источник истины

Все правила классификации должны быть определены в одном конфигурационном источнике.

Предпочтительное расположение:

`config/taxonomy.yaml`

В нём должны быть представлены:

1. Основные категории.
2. Подкатегории.
3. Синонимы.
4. OSM-теги.
5. Правила классификации.
6. Исключения.
7. Критерии значимости.
8. Признаки культурного наследия.
9. Признаки туристического назначения.
10. Приоритеты.
11. Параметры отображения.

## 11.2. Запрет дублирования

Нельзя независимо определять одни и те же категории в:
- `models.py`;
- `enrich_osm.py`;
- API;
- `app.js`;
- стилях маркеров;
- фильтрах интерфейса.

Если техническая архитектура требует представления категорий в нескольких форматах, они должны формироваться из единого источника либо проверяться автоматическими тестами на согласованность.

## 11.3. Пример логической структуры конфигурации

Ниже приведена иллюстрация структуры, а не требование использовать именно этот YAML-синтаксис.

```yaml
taxonomy:
  historical_heritage:
    label: "Историческое наследие"
    subcategories:
      railway_heritage:
        label: "Железнодорожное наследие"
        object_classes:
          - heritage
          - tourism
        osm_rules:
          - historic=locomotive
          - historic=railway_station
          - railway=museum

      monuments_memorials:
        label: "Памятники и мемориалы"
        osm_rules:
          - historic=monument
          - historic=memorial

  cultural_institutions:
    label: "Культурные учреждения"
    subcategories:
      historical_museums:
        label: "Исторические музеи"
        osm_rules:
          - tourism=museum

settings:
  railway_radius_meters: 2500
  require_description_at_high_zoom: true
```

Реальные правила должны учитывать сочетания тегов и контекст.

Например, `railway=station` без дополнительных признаков не должен автоматически классифицироваться как железнодорожное наследие.

# 12. Требования к структуре базы данных

## 12.1. Общие требования

Существующая модель данных должна быть адаптирована так, чтобы поддерживать новую таксономию без потери исходной информации.

Окончательную структуру должен предложить Claude после изучения моделей и текущих миграций.

Предварительно необходимы следующие логические поля:

| Поле | Назначение |
|---|---|
| `type1` | Основная группа, если она сохраняется в архитектуре |
| `type2` | Конкретная категория или подкатегория |
| `object_class` | `heritage`, `tourism`, `both`, `unclassified` |
| `excluded_from_map` | Флаг исключения |
| `exclusion_reason` | Причина исключения |
| `priority` | Приоритет отображения |
| `short_description` | Краткое содержательное описание |
| `description_source` | Источник описания |
| `description_quality` | Результат проверки качества |
| `osm_type` | Тип исходного OSM-объекта |
| `osm_id` | Идентификатор исходного OSM-объекта |

Допускается изменение названий и структуры полей в соответствии с существующей архитектурой.

## 12.2. Сохранение ручной классификации

**Критически важное требование: автоматический импорт не должен уничтожать ручные изменения.**

Если объект вручную:
- исключён из карты;
- отнесён к определённой подкатегории;
- получил уточнённый класс;
- направлен на ручную проверку;

повторный импорт не должен безусловно перезаписывать эти значения.

Рекомендуется предусмотреть:
- `classification_source`;
- `classification_locked` или аналогичный механизм;
- `manual_override`;
- дату последней автоматической классификации.

Конкретная модель должна быть выбрана с учётом существующей схемы.

## 12.3. Идемпотентность

Повторный импорт одного и того же OSM-объекта не должен:
- создавать дубликаты;
- сбрасывать ручные исключения;
- заменять подтверждённую классификацию автоматической;
- удалять описание без причины;
- менять статус объекта на основании отсутствия данных в очередном источнике.

При конфликте обновление должно сохранять более приоритетные и подтверждённые сведения.

## 12.4. PostgreSQL ENUM

Если `Type2` реализован как PostgreSQL ENUM, изменение списка значений требует отдельного рассмотрения миграций.

`create_all` не должен считаться достаточным механизмом изменения существующего ENUM.

Claude должен определить:
- какие значения добавляются;
- какие значения устаревают;
- нужна ли миграция существующих записей;
- требуется ли изменение типа хранения;
- как обеспечить совместимость со старой схемой.

Запрещается выполнять разрушительную миграцию без резервного сценария.

# 13. Требования к API

## 13.1. Фильтры

API получения объектов карты должно учитывать:

1. `bbox`;
2. `zoom`;
3. `excluded_from_map`;
4. расстояние до железнодорожной линии;
5. качество `short_description`;
6. приоритет отображения;
7. категорию и подкатегорию, если фильтрация по ним предусмотрена интерфейсом.

## 13.2. Исключённые объекты

Запрос пользовательского слоя не должен возвращать записи с:

`excluded_from_map = true`

Исключение допустимо только для специальных административных или диагностических endpoint, если они существуют в проекте.

## 13.3. Описание на крупных масштабах

При zoom, для которого действует требование содержательного описания, API не должно возвращать объекты с невалидным `short_description`.

## 13.4. Производительность

Необходимо проверить текущую реализацию `/api/culture_places`.

По предварительным сведениям Claude:
- endpoint возвращает все объекты в bbox;
- не принимает zoom;
- выполняет дополнительные запросы для получения координат каждой строки.

Следует рассмотреть:
- устранение N+1 запросов;
- получение координат одним SQL-запросом;
- использование существующих пространственных индексов;
- применение фильтров до сериализации;
- сокращение объёма ответа.

Нельзя менять контракт API без проверки фронтенда и всех существующих потребителей.

# 14. Требования к фронтенду

## 14.1. Категории

Фронтенд должен получать согласованные идентификаторы и названия категорий.

Не допускается ситуация, когда:
- API возвращает одну категорию;
- фильтр интерфейса показывает другую;
- стиль маркера использует третье название.

## 14.2. Синонимы

В интерфейсе пользователь должен видеть понятные объединённые категории.

Исходные подтипы могут сохраняться для карточки объекта или дополнительной информации.

## 14.3. Стили маркеров

Стили должны соответствовать новой таксономии.

Необходимо проверить:
- `type2Labels`;
- `type2DescriptionLabels`;
- `MARKER_STYLE`.

Если эти структуры дублируют конфигурацию таксономии, следует устранить дублирование либо добавить механизм проверки согласованности.

## 14.4. Масштабирование

Фронтенд должен:
- передавать zoom в API;
- реагировать на `zoomend`;
- не показывать исключённые объекты;
- не показывать объекты без содержательного описания на крупных масштабах;
- сохранять корректную работу кластеризации;
- не создавать лишние запросы при перемещении и масштабировании карты.

Каждый объект получает понятную категорию и подкатегорию из единой системы.

**4. Синонимичная группировка.**  
Близкие типы объединяются для интерфейса, но исходная информация сохраняется.

**5. Самостоятельное железнодорожное наследие.**  
Исторические вокзалы, паровозы и железнодорожные музеи должны быть корректно выделены.

**6. Разделение наследия и туризма.**  
Один объект может относиться к одному или обоим классам, но эти признаки не смешиваются.

**7. Отказ от автоматического отображения `monument`.**  
Каждый памятник должен пройти классификацию и проверку значимости.

**8. Качественные описания.**  
На крупных масштабах отображаются только объекты с содержательным `short_description`.

**9. Сохранение исходных данных.**  
Исключение из карты не означает удаление записи.

**10. Защита ручных изменений.**  
Автоматические процессы не должны уничтожать подтверждённые решения.

**11. Единый источник правил.**  
Таксономия и правила классификации не должны дублироваться по всему проекту.

**12. Минимальные изменения архитектуры.**  
Существующий рабочий код должен адаптироваться, а не переписываться без необходимости.

**13. Проверяемость.**  
Каждое существенное требование должно иметь тест или измеримый критерий приёмки.

**14. Поэтапная реализация.**  
Изменения выполняются последовательно, с проверкой каждого этапа.

# 23. Финальное условие

Цель разработки — не просто сократить количество отображаемых маркеров.

Необходимо создать устойчивую систему, которая понимает разницу между:
- культурным наследием;
- туристическими достопримечательностями;
- обычными объектами инфраструктуры;
- локальными памятными объектами;
- историческими железнодорожными объектами;
- техническими и случайными точками OSM.

Итоговая система должна обеспечивать не максимальное количество найденных объектов, а **максимальную полезность и достоверность объектов, представленных пользователю**.

Copilot должен считать этот документ основным набором функциональных и архитектурных ограничений для данной задачи. При этом фактическая структура репозитория и существующие контракты имеют приоритет над предположениями, сделанными в этом документе: любые расхождения должны быть выявлены и согласованы с Claude до реализации.
